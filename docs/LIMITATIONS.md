# 已知限制

这份文档把"`memscope` 做不到什么"写清楚。一个诊断工具如果不说明自己的
盲区，它的结论就不可信。

---

## 硬性限制

### 1. 只能在 Windows 上采集

依赖的 API（`psapi` / `toolhelp32` / `pdh` / `advapi32`）都是 Windows 专有的。

在其它平台上运行会明确报错并返回退出码 2：

```
错误: memscope 的采集功能依赖 Windows API，当前平台是 'linux'。
归因与分析算法本身是跨平台的（见 tests/），但没有 Windows 就采不到数据。
```

**但归因与分析部分是纯逻辑**，可以在任何平台导入和使用
（CI 里 ubuntu / macos 任务会跑这部分测试）。

### 2. 系统保护进程读不到任何信息

一台典型机器上，约**一半**的进程无法打开（`OpenProcess` 返回拒绝访问）：
`System`、`Registry`、受保护的服务宿主、反作弊驱动的进程等。

对这些进程，`memscope` 拿不到内存明细、路径、版本信息、命令行。

**处理方式**：它们被合并成一个「系统保护进程」桶，而不是拆成上百条
名字都是猜的碎片记录。这个桶的置信度标为「低」。

**这意味着**：如果你怀疑某个受保护进程有问题，`memscope` 帮不上忙——
需要用 Process Explorer 以管理员身份运行，或者用内核调试器。

### 3. 不以管理员身份运行时，看到的会更少

以普通用户身份运行时，能打开的进程更少。想要完整视图需要管理员权限，
但**本项目不会主动请求提权**——那会让"只读工具"的承诺变得可疑。

### 4. 不修改任何系统状态

这不是缺陷，是**设计**。`memscope` 不调用 `EmptyWorkingSet`，
不清空待机列表，不调整进程优先级，不终止任何进程。

它只读计数器、读进程信息、写自己的采样文件。

## 归因的固有限制

### 5. 宿主进程已退出时，共享运行时无法确定归属

WebView2 的渲染进程可能比宿主活得久。父进程链一断，`memscope` 只剩
`--user-data-dir` 这类命令行线索可用。线索也没有时，这些进程会被放进
「未归因的共享运行时」分组并标为低置信度。

**这不是能修好的问题**——信息确实不存在了。能做的是**不猜**。

### 6. 同一个可执行文件被多个产品复用

某些运行时、安装器、更新程序就是被多个软件共用的。按名字合并会错，
不合并也会错。`memscope` 的策略是**优先看厂商与产品签名**，
都没有时才退回路径——并在证据里写明用了哪条规则。

### 7. PID 重用且拿不到启动时间时，假父子关系无法识别

识别假父子关系的唯一可靠依据是"子进程不可能比父进程先出生"。
如果两个进程的启动时间都取不到（受保护进程），这条校验就失效。

### 8. 产品族合并是启发式的

"同厂商 + 产品名互为前缀且边界在词上"这条规则能处理
`Steam` / `Steam Client WebHelper`，也能避免 `EA` 吞掉 `Eagle`，
但它**不可能对所有软件都正确**。

刻意做的一个取舍：**只在同一厂商内部合并**。跨厂商绝不合并，
即使产品名完全一样。

### 9. 后台软件分类只做关键词匹配

`diagnose.py` 里那张"游戏平台 / 外设驱动 / 远程控制"的表是硬编码的关键词。
它**会认错**：

- 名字里恰好含关键词的软件会被误判
- 换了名字的软件会被漏掉
- 中文名与英文名都要分别列（比如 `AweSun` 和 `向日葵`）

所以报告里的措辞是"检测到…可能不需要常驻"，并且明确写出
"本分类只按厂商/产品名做关键词匹配，**可能认错**——请自己核对列表再决定"。

## 分析的固有限制

### 10. 泄漏检测需要足够长的采样窗口

判定门槛是硬编码的：

```python
MIN_SAMPLES = 8             # 至少 8 个采样点
MIN_SPAN_SECONDS = 120.0    # 跨度至少 120 秒
```

样本不足时**明确拒绝下结论**，而不是硬给一个结果。

但即使满足门槛，一个小时的窗口也只能发现"每小时涨几百 MB"这种明显泄漏。
缓慢的泄漏（每小时几十 MB）需要数小时甚至数天的采样。

### 11. "在增长"不等于"有 bug"

缓存、连接池、会话表、JIT 编译产物、碎片整理都会正常增长到一个稳定平台。

`memscope` 用 R² 来区分"持续单调增长"与"随机波动"，但**无法区分
"会收敛的增长"与"不收敛的泄漏"**——那需要更长的观察窗口。

报告里明确写了这一点，并且建议延长采样验证。

### 12. 线性回归对非线性增长不敏感

只拟合直线。如果某个程序的内存是"阶梯式增长"（比如每次打开文件涨一点），
或者呈指数增长，线性拟合的 R² 会偏低，可能漏报。

### 13. 采样期间应用可能重启

如果被采样的程序在采样窗口内重启了，它的内存序列会出现一个"断崖"。
当前实现**不检测重启**——那条序列的拟合结果会失真，通常表现为
斜率被拉低或 R² 变差。

## 性能

| 操作 | 耗时（350 进程的机器） |
|---|---|
| 首次完整快照 | 约 0.7 秒 |
| 后续快照（缓存命中） | 约 0.2 秒 |
| 采样每次开销 | 约 0.2 秒 |

缓存键是 `(pid, 启动时间)`——进程生命周期内不变的字段（路径、命令行、
版本资源）只读一次。

**采样间隔不要设得低于 1 秒**：采集本身要 0.2 秒，间隔太短会让
`memscope` 自己成为明显的负载来源。默认 5 秒是合理的。

## 输出与环境的坑

### 14. PowerShell 的 `>` 重定向会写成 UTF-16

这是 PowerShell 的行为，不是 `memscope` 的问题，但很容易踩：

```powershell
python -m memscope --json > out.json     # ✗ 变成 UTF-16LE + BOM
```

下游工具读这个文件会报 `Unexpected UTF-8 BOM`。正确做法：

```powershell
python -m memscope --json | Out-File -Encoding utf8NoBOM out.json   # ✓
# 或者用 cmd
cmd /c "python -m memscope --json > out.json"                        # ✓
```

程序自己输出的是干净的 UTF-8，用 Python 直接捕获或写入文件都没有这个问题。

### 15. 终端编码

`memscope` 启动时会把 stdout/stderr 重配为 UTF-8，所以中文输出不会崩。
但如果你的终端字体不支持中文字形，会显示成方块——那是字体问题，
不是编码问题。

## 发现新问题？

欢迎提 [Issue](https://github.com/Ray144165154/memscope/issues)。

提归因错误时，请附上：

1. `memscope --explain <PID>` 的输出（它会打印完整的推理依据）
2. 你期望的归因结果
3. **如果可以**：`memscope --json` 里对应的那条记录

有了这三样，归因问题通常能直接定位到是哪条规则需要调整。

**请自行检查输出里是否包含不想公开的信息**（用户名、安装路径等）。
