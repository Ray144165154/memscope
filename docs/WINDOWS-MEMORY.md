# Windows 内存模型

这份文档解释 `memscope` 每一条结论背后的原理。读完它，你会明白为什么
很多"内存优化"软件做的事情是**反效果**的，以及应该看哪些指标。

---

## 一、先破除一个几乎所有人都有的误解

任务管理器或者各种"内存监控"上那个"可用内存"数字，**不是"剩余内存"**。

Windows 的设计哲学是：**空闲的内存就是浪费的内存**。任何一段物理内存，
只要暂时没人用，系统就会拿它去缓存磁盘上的数据——因为说不定你马上就
要用到。这块缓存叫**待机缓存（standby cache）**。

于是出现了一个反直觉的现象：

```
可用内存   3.3 GB
空闲内存   0.04 GB     ← 看起来"内存快用光了"
待机缓存   3.3 GB     ← 其实这 3.3 GB 随时能立刻交出来
```

**空闲内存接近 0，在 Windows 上是健康的，不是故障。**

如果一段内存既没被程序使用、也没被用作缓存，那才是浪费。
系统会尽可能避免这种情况。

### 这意味着什么

一个只盯着"空闲内存"的工具，在你机器一切正常时也会报告"内存严重不足"，
然后提供一个"释放"按钮。点下去，它把待机缓存丢掉——
于是系统失去了有价值的磁盘缓存，下次读同样的数据还得去硬盘拿。
**数字变好看了，系统变慢了。**

`memscope` 的做法是把"使用中 / 待机缓存 / 空闲"三段**并列**展示，
而不是把空闲那段单独画成一条几乎空掉的红色进度条。

## 二、三个容易混淆的概念

### 工作集（Working Set）

进程当前**映射在物理内存里**的页面总量。

它是**会被系统随时调整**的：你切到别的程序，当前程序的工作集可能被
悄悄裁掉一部分（那些页面被移到待机列表或写入页面文件）。所以工作集
**波动很大**，不适合用来判断"这个程序占了多少内存"。

### 私有字节 / 提交量（Private Bytes / Commit）

进程**向系统申请**的内存总量。它包含：

- 已经在物理内存里的部分
- 被换出到页面文件的部分
- 尚未真正写入（已保留）的部分

**这个数字才是"这个程序要求系统为它准备多少内存"**，也是任务管理器里
"内存"那一列的语义。它比工作集稳定得多。

`memscope` 默认用**私有字节**排序和展示，原因就在这里。

> 顺带说明：Windows 允许程序申请超过物理内存总量的内存（超额提交），
> 因为程序申请了不代表马上就会全部用到。这是一个特性，不是 bug。

### 提交上限（Commit Limit）

**物理内存 + 页面文件大小**。系统最多能"承诺"出去的内存总量。

这是真正的红线：一旦提交量触到提交上限，**新的内存申请会直接失败**，
程序会报"内存不足"甚至崩溃——哪怕物理内存看起来还有空余。

---

## 三、真实的约束：提交量 vs 物理内存

这是 `memscope` 最看重的一个指标。

```
物理内存总量   15.18 GB
提交量         20.26 GB      ← 比物理内存还多
超出部分        5.08 GB      ← 这 5 GB 只能待在页面文件里
```

**提交量超过物理内存，意味着有相当一部分程序数据不在内存里。**
程序一旦访问到那部分数据，CPU 会触发一个**硬缺页（hard fault）**：
暂停当前指令，把页面从硬盘读回内存，然后继续。

单次硬缺页的延迟在**微秒到毫秒级**。听起来不多，但程序在做一件事时
可能触发成千上万次。表现出来就是：

- 切换窗口时的卡顿
- 程序响应变慢、鼠标转圈
- 硬盘灯狂闪

### 为什么这时候加内存比"优化"有效

如果这 5 GB 能被放进物理内存，硬缺页就基本消失了。
这是唯一真正能"优化内存使用"的办法之一：**让工作集装得下**。

要么加内存，要么减少常驻程序——`memscope` 的作用就是告诉你
**哪些程序值得关**。

## 四、分页列表：Windows 到底怎么管内存

物理内存里的每一页（x86/x64 上是 4 KB）都处在某个"列表"上：

| 列表 | 含义 | 能否立即回收 |
|---|---|---|
| **Active（活动）** | 正在被进程使用 | 否 |
| **Standby（待机）** | 有效数据，但当前没人用（就是磁盘缓存） | **能，立即** |
| **Modified（修改）** | 改过但还没写回磁盘 | 需要先写盘 |
| **Free（空闲）** | 内容无意义，但还没清零 | 需要清零才能用 |
| **Zeroed（零页）** | 已清零 | **能，立即** |

待机列表还分 8 个优先级，从"最不可能被再次使用"到"最可能被再次使用"。
`memscope` 展示的三个待机数字就对应不同优先级：

- **核心（Core）** —— 优先级最低，最先被回收
- **常规（Normal Priority）** —— 主体部分
- **保留（Reserve）** —— 优先级最高，系统尽量不动它

这个分层的意义是：当程序需要内存时，系统从优先级最低的待机页开始回收，
**尽量保留那些最可能被再次用到的缓存**。

> 待机缓存里的数据是**有效**的——被回收时不需要写盘、不需要重新计算，
> 直接换个归属就行。所以"把待机缓存给程序用"和"把空闲内存给程序用"，
> 速度上**没有区别**。

## 五、为什么"内存清理"软件是有害的

现在可以完整解释这件事了。

### 它们做什么

主流做法是调用 `EmptyWorkingSet()` 或 `SetProcessWorkingSetSize()`，
把进程的工作集**强行清空**。

### 发生了什么

1. 那些页面被标记为可回收，转移到待机列表或写入页面文件
2. **"可用内存"数字上升了，任务管理器里的进度条变绿了**
3. 程序下一瞬间又需要这些数据
4. 如果页面还在待机列表里 —— 运气好，代价很小
5. 如果已经被写到页面文件、或者被后续的内存申请挤掉了 ——
   **触发硬缺页，必须从硬盘读回来**
6. 硬盘狂转，程序卡顿

### 净效果

**内存数字变好看了，系统变慢了。** 而且这个"优化"是**完全可逆地无意义**——
系统本来就会在真正需要内存时自动做同样的事，只是在它认为合适的时机做。

### 还有一个更隐蔽的害处

如果这类工具是**定时自动清理**的，它就在持续地破坏系统的缓存策略：

- 系统精心维护的、预测你下一步会用到什么数据的缓存，被反复丢弃
- 每次都要从硬盘重新建立
- 长期下来，整个系统的 I/O 效率都在下降

### 那什么是有用的？

| 做法 | 是否有效 | 说明 |
|---|---|---|
| 关闭不需要的常驻程序 | ✅ **最有效** | 直接减少提交量 |
| 减少开机自启项 | ✅ **最有效** | 从源头解决 |
| 加内存 | ✅ **最直接** | 如果预算允许 |
| 把页面文件放到 SSD | ✅ 有效 | 减少硬缺页的代价 |
| 定时"释放内存" | ❌ **有害** | 见上文 |
| 清理待机缓存 | ❌ **有害** | 丢掉有价值的磁盘缓存 |
| 手动修剪工作集 | ❌ **有害** | 制造硬缺页 |

## 六、内核池：一个经常被忽略的地方

内核内存分两块：

- **分页池（Paged Pool）** —— 可以被换出到页面文件
- **非分页池（Nonpaged Pool）** —— **不能**被换出，必须常驻物理内存

正常量级是几百 MB。如果非分页池持续增长到 GB 级，通常意味着
**某个驱动程序存在内存泄漏**——它申请了内存却从不释放。

这块内存很特殊：

- 它**不被任何进程"拥有"**，任务管理器的进程列表里看不到
- 它**不能被换出**，直接蚕食可用物理内存
- 它由驱动占用，用户态无法干预

`memscope` 会报告这个数字，并且建议用采样分析来确认它是否在增长。

---

## 七、那么，正确的诊断方法是什么

按这个顺序看：

### 1. 提交量 vs 物理内存

```
提交量 > 物理内存  →  系统在依赖页面文件，卡顿的根源在这里
```

这是第一优先级。如果这一条不成立，说明内存根本不是瓶颈
（那卡顿就另有原因：CPU、磁盘、GPU、或者某个程序自己写得太差）。

### 2. 谁贡献了最多的提交量

按应用归因后看排行。注意三点：

- **看私有字节，不要看工作集**（工作集波动大）
- **要看整个应用，不是单个进程**：Steam 是 1 个主进程 + 7 个助手进程
- **警惕共享运行时**：21 个 `msedgewebview2.exe` 可能分属好几个不同的宿主应用，
  算到"Edge"头上是错的

### 3. 有没有东西在持续增长

一次快照看不出泄漏。需要持续采样，然后看**斜率**和**拟合优度**：

- 斜率 = 每小时增长多少
- R² 接近 1 = 增长是持续的、单调的，像泄漏
- R² 很低 = 只是正常的申请/释放波动

```bash
memscope watch -i 10 -d 3600 -o samples.jsonl
memscope analyze samples.jsonl
```

> 注意：**"在增长"不等于"有 bug"**。缓存、连接池、会话表都会正常增长
> 到一个稳定平台。建议延长采样窗口，观察它是否会自行收敛。

### 4. 内核池有没有异常

如果非分页池在长，那是驱动问题，需要在驱动层面排查。

## 八、这张表值得记住

| 指标 | 该关注吗 | 原因 |
|---|---|---|
| 空闲内存接近 0 | ❌ 不用担心 | Windows 用闲置内存做缓存，这是特性 |
| 待机缓存很大 | ❌ 不用担心 | 越大说明缓存做得越好 |
| **提交量 > 物理内存** | ✅ **重点关注** | 硬缺页的来源，卡顿的根源 |
| **提交量接近提交上限** | ✅ **重点关注** | 新程序会申请失败 |
| **物理可用 < 10%** | ✅ 关注 | 系统频繁回收页面 |
| 工作集很大 | ⚠️ 参考 | 会被系统自动调整，波动大 |
| **私有字节很大** | ✅ 关注 | 这才是程序真正要走的量 |
| **非分页池 > 1 GB** | ✅ 关注 | 可能有驱动泄漏 |
| **某个应用私有字节持续增长** | ✅ 关注 | 可能是泄漏，需延长采样确认 |

## 关于本工具的一个说明

`memscope` **不会**、也**不打算**去"释放内存"。

它做的三件事都是只读的：读取系统计数器、读取进程信息、记录时间序列。
它不调用 `EmptyWorkingSet`，不清空待机列表，不修改任何进程状态。

这也是你可以放心把它的结论拿去核对的原因——**它没有动机让数字变好看**。
